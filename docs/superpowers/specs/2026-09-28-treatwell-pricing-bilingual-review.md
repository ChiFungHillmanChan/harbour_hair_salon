# Treatwell 價目與全站中英文：設計審閱

日期：2026-09-28。分支：`codex/core-web-vitals`。

審閱對象：[設計草稿](docs/superpowers/specs/2026-09-28-treatwell-pricing-bilingual-design.md)。本文件記錄設計缺口及建議，未批准新的業務政策，也不是實作完成報告。

結論：草稿已清楚界定雙語範圍、Treatwell 定價來源及歷史資料保護原則；但要成為可直接執行的規格，仍需補足價格交易、服務對應、表單狀態生命週期及內容發布流程。最需要先處理的是：調整現行服務價，可能透過沒有價格快照的舊預約影響佣金計算。

本次只讀取本地原始碼、schema、seed 與已安裝的 Next.js 指南，新增這份審閱文件。沒有連接正式資料庫、重新登入 Treatwell 核價、更新外部平台、執行 migration 或部署。因此下文的 seed 差異不代表正式網站一定有相同資料，也不能據此宣稱受影響預約的數量。

## 需要先補足的設計

### 1. 歷史價格保護須涵蓋通知、後台及佣金

草稿第 4 節已指出顧客頁會以現價替代空白的 `priceAtBooking`；相同回退也存在於通知、排程及薪酬。若一筆已完成預約沒有快照，更新服務價後重算未定案的薪酬期間，佣金基礎可能改變。已定案期間目前有禁止直接重算的保護，不能描述成所有已發薪紀錄都會自動變動。

依據：[薪酬計算](src/app/services/payroll-service.ts:52)、[佣金收入來源](src/app/services/payroll-service.ts:71)、[通知快照](src/app/services/notification-outbox-service.ts:38)、[後台價格顯示](src/components/admin/ScheduleCalendar.tsx:247)。

建議補入：更新價目前，盤點空白快照的預約及其涉及的薪酬期間、待發通知；有可信歷史證據才補記金額及來源。無證據時保留「歷史金額未確認」，不要以現價或零元補齊。顯示、通知及受影響佣金的處理須一致，受影響薪酬不能無提示地繼續採用現價。

此外，若新價格屬諮詢後可調整的報價，須釐清它是否仍能作為佣金基礎；這是金額語意的業務決定，不應在雙語改動中順帶改變既有薪酬公式。

### 2. 「同一價格版本」需要完整的伺服器報價規則

草稿已有版本及快照原則，但尚未定義選項、優惠、稅項及價格變更如何一起確定。現有顧客預約會先套用全站優惠，再套優惠碼；管理員新增或更換服務也會套全站優惠。只加 NHS 顯示欄位，不能保證預約記錄仍是核對過的 NHS 金額。

依據：[顧客計價](src/app/services/booking-service.ts:292)、[自動分配造型師計價](src/app/services/booking-service.ts:418)、[管理員更換服務](src/app/actions/admin-schedule.ts:164)、[管理員新增預約](src/app/actions/admin-schedule.ts:327)。

建議定義共用報價結果：服務／髮長選項 ID、一般或 NHS 類型、價目版本、基礎金額、適用優惠及扣減、附加項目、稅項狀態、價格性質，以及實際承諾的金額。這些是資料契約要求，未指定必須採用哪一種資料表設計。

提交時由伺服器核對選項、資格、可用狀態及版本；若顧客看價後價目或優惠已改，顯示新報價並要求重新確認，不默默以新價建立預約。語言切換不更改報價；單純改期與更換服務分開規定。GBP 的精度及捨入方式由共用計價邏輯決定。

「不疊加平台折扣」與「網站優惠是否適用」需要在規格中分開。店主未確認後者前，不應把現有全站自動折扣直接套到新 NHS 選項。

### 3. 需要逐筆服務對應與退役機制

草稿要求保留原 ID，但未說明核對表以外的舊服務如何處理。本地 seed 仍有半頭冷燙 NHS £129、全頭冷燙 NHS £159，以及 Hair Correction／Keratin／Paimore NHS £198；這些不在草稿已確認的 NHS 價目中。Seed 亦有 £10 造型項目，不能直接認定它們就是 £20 Special Set。

依據：[既有服務 seed](prisma/seed.ts:79)、[Service 模型](prisma/vercel/schema.prisma:83)、[公開服務查詢](src/app/services/page.tsx:23)、[預約服務查詢](src/app/book/page.tsx:42)。目前 Service 沒有正式的公開／可預約／退役狀態，查詢也沒有按這些狀態篩選。

建議建立人工核對表，逐筆記錄現有 ID、Treatwell 原始項目／選項識別、原名、一般與 NHS 配對、髮長、時長、VAT 證據、價格性質、核對日期及處理結果。能取得來源 ID 時使用 ID；不能取得時保留足以定位的人工證據，不以中文名稱配對。

將「保留歷史關聯」與「允許新預約」分開。未確認及退役選項可保留原記錄，同時從新預約與公開報價排除；伺服器亦須拒絕直接提交已停用選項。不能只在畫面隱藏，也不能把清空描述或改名當成正式退役。

### 4. 兩個敏感測試與附加項目會影響預約行為

草稿把兩個 £15 項目的分別列作待確認，還需要指出對現有資格判斷的影響：服務轉介使用第一個 `isPatchTest` 記錄，染髮資格查詢則接受所有帶此標記的服務。若把兩個來源項目都直接標記，可能轉介到不適用的測試，或讓原本不適用的完成紀錄滿足資格。

依據：[轉介選取](src/app/services/consultation-routing.ts:24)、[資格查詢](src/app/services/booking-service.ts:462)。

建議先確認每個測試的用途及適用服務，再決定明確的轉介／資格關聯。未確認的來源項目不自動取得資格用途，也不因同價而合併；本次不推導或修改敏感測試的時間政策。

Special Set 的 £20 已確認，但仍欠：可搭配哪些主服務、能否單獨預約、數量上限、是否增加時間、NHS／優惠適用與稅項。`Adds Extra Long` £37 也需同樣的選取規則。現有一筆預約只有一個 `serviceId`，沒有附加項目明細；必須決定本期僅展示附加價，還是提供真正的預約選取及快照。

### 5. 語言路由與表單保留需要先證明可同時成立

草稿要求 `/zh-hk/` 路由與切換時保留未儲存資料，但未決定狀態放在哪個不會被切換卸載的位置。預約流程使用元件內的 `useState`，服務表單使用 `defaultValue`，MFA 復原碼只在 `useActionState` 結果中顯示。把同一個元件放到兩個網址，並不保證原狀態仍在。

依據：[預約狀態](src/components/booking/BookingWizard.tsx:42)、[服務表單](src/components/admin/ServiceForm.tsx:62)、[MFA 一次性結果](src/components/auth/AdminMfaForms.tsx:21)、[MFA 頁面保留元件的既有處理](src/app/auth/mfa/setup/page.tsx:11)。已安裝的 [Next.js layout 指南](node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/layout.md:142) 亦指出跨 root layout 會整頁載入。

建議先以預約、未儲存服務表單、MFA 復原碼三個代表流程驗證架構。規格須列明共用版面及狀態容器的位置、元件是否會重新掛載、返回／前進行為，以及登出或切換帳戶時的清除時機。敏感資料只留在必要的頁面記憶體，不放 URL、localStorage、sessionStorage 或持久快取；也不把「自動提交以免遺失」當成解法。

若選定路由架構無法保證 MFA 原頁面狀態存續，須調整切換機制或重新討論該流程需求，不能把復原碼重新產生當成補救。

### 6. 中文路由需一份明確的授權與跳轉對照

草稿已有權限一致的要求，但還沒有落到路由規則。現有 middleware 的 matcher 及判斷使用 `/admin`、`/appointments`、`/kiosk` 等英文路徑，登入、MFA 及 Google callback 亦有固定英文跳轉。加入中文路由時只翻譯 Link 不足夠。

依據：[middleware 判斷](src/middleware.ts:53)、[matcher](src/middleware.ts:120)、[登入跳轉](src/app/actions/auth.ts:67)、[Google callback](src/app/api/auth/google/callback/route.ts:96)。這是新增中文路由的設計風險，並非本次證明現有網站存在權限繞過。

建議將「辨識並驗證語言前綴 → 取得不含語言的業務路徑 → 執行原權限政策 → 建立保留語言的安全回跳」寫成明確順序，並列出 Server Action、MFA 未完成、失效 kiosk 裝置及直接輸入網址的驗收案例。API、OAuth callback、cron、ICS 保持原有機器路徑；不用把語言 cookie 當作權限資訊。

保留 `/book` 先判斷預約是否開放、再要求登入的順序。路由擴大後，亦不應無意令每個公開頁都查詢帳戶或資料庫。草稿中的 MFA 是現有管理員 MFA 的翻譯範圍，不應被解讀為新增顧客 MFA 功能。

## 應補入規格的其他事項

### 7. 翻譯「完整」不等於兩種語言是同一個已發布版本

草稿建議兩種語言齊備才發布，但未定義已發布內容修改後的狀態。現有服務及網誌儲存會直接更新原記錄；只加翻譯欄位及完整度，可能讓英文新政策立即上線，中文仍是舊政策，或讓儲存中文草稿覆寫正式內容。

依據：[服務儲存](src/app/actions/admin-services.ts:108)、[網誌儲存](src/app/actions/admin-blog.ts:215)。

建議預設：儲存草稿與發布分開；英文內容改動後，對應中文可標記「需重新校對」；發布時將同一修訂的兩種語言一起啟用，未完成期間繼續顯示上一個完整版本。服務、FAQ、分類、首頁及優惠等目前沒有相同發布模型的內容，也須說明如何遵守此原則。首次上線的內容清單應包含資料庫內容、程式內預設文案、巢狀 JSON 區塊及圖片替代文字。

是否採用上述成對發布政策，仍由店主確認。共享價格更新若與說明或政策修訂相關，也需避免只發布其中一部分。

### 8. 通知語言需要來源優先順序與舊事件相容策略

「該次事件的語言」仍有歧義：中文預約由英文介面的管理員確認、顧客之後更改個人偏好、定時提醒沒有操作員時，應採用哪一種語言？現有 outbox 先儲存預約內容，首次發送前才產生並固定電郵內容，所以排入隊列與首次寄出的時點不同。

依據：[排入隊列](src/app/services/notification-outbox-service.ts:38)、[固定寄件內容](src/app/services/notification-outbox-service.ts:111)。

建議預設：以預約記錄的通知語言建立顧客事件快照；店方通知使用獨立設定；密碼重設使用發起流程的語言；既有無語言事件維持英文。個人偏好是否影響尚未建立的後續事件須另行決定，不能讀取最後操作管理員的介面語言。

已固定寄件內容的重試保留原內容與事件識別，不以更新翻譯為由重建。舊 payload 缺少 VAT 或價格類型時不能假設已含稅／一般價。即使全套電郵雙語化延後，新價格的語意及快照相容仍屬本期定價必要工作。

### 9. 驗收還要包含結構化資料與伺服器錯誤

目前服務列表及分類頁的 JSON-LD 直接輸出 `service.price`，畫面上的稅項與 NHS 說明不會自動進入這些資料。後台及預約動作亦直接回傳英文錯誤訊息，僅翻譯畫面標籤會留下英文驗證結果。

依據：[列表 JSON-LD](src/app/services/page.tsx:89)、[分類 JSON-LD](src/app/services/[slug]/page.tsx:130)、[服務驗證錯誤](src/app/actions/admin-services.ts:65)、[預約錯誤](src/app/actions/booking.ts:338)。

建議把 JSON-LD、首頁精選、分類最低價／價格區間、優惠橫幅一起列入價格輸出清單；不能把有限資格的 NHS 價冒充人人適用的最低價。可預期錯誤以穩定代碼及參數配合字典呈現，系統原始診斷保留原文，避免依英文錯誤字串反推翻譯。

另需確認 SSR 的 HTML lang、canonical、hreflang、Open Graph、sitemap 與實際網址一致，公開未翻譯內容不落入英文預設文案而被誤當成完成。個人偏好不得覆蓋明確網址的語言；記住偏好的用途須寫清楚。公開頁快取驗收包括實際快取命中、資料庫查詢量及雙語失效，不只測版面移動。已安裝的 [cookies 指南](node_modules/next/dist/docs/01-app/03-api-reference/04-functions/cookies.md:69) 說明在 layout／page 讀取 cookie 會影響動態渲染。

## 建議增加的驗收案例

| 場景 | 必須觀察的結果 |
|---|---|
| 舊預約缺少價格快照後更新服務價 | 顧客頁、後台、通知及未定案薪酬不默默改用新價；未知資料仍可識別 |
| 一般／NHS × 有無全站優惠 × 有無優惠碼 | 每組依核准規則計價，前後台及電郵一致；無 NHS 的服務不能偽造選項 |
| 瀏覽報價後價目或優惠改動，再提交 | 明確提示重新確認；不默默換價，不建立重複預約 |
| 僅改期／更換服務／更換價格選項 | 分別符合保留或重建報價規則，通知與快照同步 |
| 停用舊服務後從舊頁面直接提交 ID | 新預約被拒絕；歷史關聯及已存在預約仍可讀取 |
| 兩個敏感測試與不同主服務 | 只接受已確認的轉介及資格關聯，不取第一個相似記錄 |
| 預約、未儲存後台表單及 MFA 結果頁切換語言 | 資料、一次性結果及步驟保留；不提交、不重建復原碼、不持久儲存敏感資料 |
| 中文直接網址、登入／登出、Google、MFA、過期 kiosk | 權限與英文一致；回跳保留語言且仍經安全驗證 |
| 已發布英文改動、中文未完成或仍需校對 | 正式站依核准發布流程顯示；草稿不洩漏，也不誤報翻譯完成 |
| 中文顧客預約由英文介面管理員確認，並觸發重試 | 通知使用規定的顧客語言；重試內容及事件識別不變 |
| 兩語價格頁及失效／錯誤狀態 | HTML、JSON-LD、metadata、字典與價格條件一致；兩語快取一起更新 |

## 建議的後續順序

1. 完成業務決策表、逐筆服務對應及歷史價格影響盤點，確定哪些資料可發布、哪些仍待核對。
2. 先設計共用報價與快照、服務退役及舊資料相容規則，再設計三份 schema 的同步變更。另以代表流程驗證語言路由與狀態保留。
3. 定義內容修訂／發布及通知語言契約，建立逐頁、逐欄位翻譯清單，再分批實作與驗收。
4. 正式更新價目前，準備可審閱的更新差異、版本啟用及回退步驟。回退不能改寫已建立預約的快照，也不能將已停用的不明價格重新開放。

以上為建議順序，並非本次已執行的實作計劃。這次沒有執行應用測試或 build；設計審閱的證據來自所列原始碼及文件，未把靜態查閱表述為執行時驗證。
