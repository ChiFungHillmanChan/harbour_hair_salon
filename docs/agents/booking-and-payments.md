# Booking, deposits and operations rules

> The business rules the booking, Square deposit and operations code enforces. Owner decisions are dated. Part of the agent guide: `CLAUDE.md` / `AGENTS.md` link here. Keep it true when the code changes.

- **Booking needs a signed-in customer with a confirmed email.** `src/app/[locale]/book/page.tsx` redirects to sign-in with `?redirect=/book`, and every booking action checks again (`verifySession`, `hasVerifiedEmail`). Middleware deliberately does not gate `/book`: whether booking is open lives in the database, and middleware would need a DB read per request. While booking is closed, `/book` shows everyone the phone / Fresha / Treatwell page (`BookingClosedNotice`) — beta testers excepted (next bullet).
- **Booking needs a contact phone (owner request 2026-11-15).** The confirm step asks for one, filled from `User.phone` (sign-up keeps it optional; Google sign-ups have none). `submitBooking` takes the typed phone, else the saved one, and refuses `PHONE_REQUIRED` / `PHONE_INVALID` (`normalizeContactPhone` in `lib/phone.ts`: 7–15 digits, at most 20 characters) before any lookup, deposit or hold. A changed phone is saved to the account before the request is made, so the salon's new-request email (`SALON_ALERT`) and the Google diary entry carry it. Staff see the customer's phone and email (tap to call or email; never a walk-in or erased placeholder address) when they open a booking in Admin → Schedule (day and week views). Staff-entered bookings keep the phone optional.
- **Beta booking (owner decision 2026-10-18).** While online booking is closed to the public (`bookingEnabled` off), a signed-in account whose `User.email` is on `SiteSettings.bookingBetaEmails` gets the whole online flow, Square deposits included: `/book`'s wizard, the slot/day lookups, the price preview, `submitBooking`, and Reschedule in My Bookings. The list lives in Admin → Settings ("Beta testers", one email per line, at most 20, no walk-in/erased placeholders; `lib/booking-beta.ts`), is stored lowercase `", "`-joined, is read from the live row on every check (never the day-cached `getSiteSettings()`, and kept out of that cached object: it is personal data) and takes effect on Save; the settings audit records only how many testers. Gate (`lib/booking-maintenance.ts`): `assertOnlineBookingReady` / `isBookingEnabled` stay the public gate, unchanged; `assertOnlineBookingReadyFor(db, userId)` (booking transactions and the deposit precheck) and `isBookingEnabledFor(userId)` / `isBetaBookingOpenFor(userId)` (pages and lookups) add the beta check, which still needs the Square payments lock to be off (production credentials), the same calendar readiness and the CALENDAR_SYNC_ENABLED / receivesBookings rule — but not `NOTIFICATIONS_ENABLED`, `bookingEnabled` or the operations readiness. It does not open anything to anyone else, and admin booking paths still never call the gate. Emails: with `NOTIFICATIONS_ENABLED` off, only a tester's appointments are emailed (the customer's mail and the salon's alert, through `dispatchAppointmentNotifications`); every other customer stays email-free and the crons (reminders, the ops alert) stay off — so testers get no reminder (review requests are retired for everyone, 2026-10-18).
- **Online booking opens in production only with Square PRODUCTION credentials.** In every production build (fails closed: a missing `VERCEL_ENV` counts; only an explicit Vercel preview is exempt) `isOnlineBookingLockedForPayments` in `lib/online-booking-lock.ts` makes `assertOnlineBookingReady` / `isBookingEnabled` answer "closed" before any DB read, and Admin → Settings refuses to switch booking on, unless `parseSquareConfig(env)` succeeds with `environment === 'production'`. No config, `SQUARE_PAYMENTS_ENABLED` not `true`, sandbox credentials or a config that does not parse all stay locked. `SQUARE_DEPOSITS_WIRED = true` records that the deposit code exists; setting it back to `false` re-locks every production build whatever the config. Deposits follow `docs/superpowers/specs/2026-10-13-square-deposits-design.md` in phases: S1 (payment tables, Admin → Settings deposit policy, per-service override, `services/deposit-quote.ts`, `previewBookingQuote`), S2 (`submitBooking` authorizes the deposit as a HOLD on the card through `services/payment-attempts.ts` and ties it to the request) and S3 (`services/deposit-lifecycle.ts`: staff confirming a request CAPTURE the deposit between two Serializable transactions; declining, withdrawing or lapsing it RELEASES the hold after the change commits, and a request whose hold has run out lapses early; cancelling a confirmed booking REFUNDS it through `services/payment-refunds.ts` — staff may keep it, and since 2026-10-18 a customer's own cancellation less than 48 hours ahead keeps it, below) and S4 (below) are in. Square is never called inside a transaction, an attempt only becomes CAPTURING in a transaction that saw its request PENDING, and every closing refuses while a capture is in flight. **Production Square credentials may be set once the sandbox acceptance list in `docs/square-payments-setup.md` §4 has passed on `main`** — every item on a local production build, plus the owner's short check on a Preview (3-D Secure with the console open, Square's own webhook, a refund, a decline; owner decision 2026-10-17, runbook §4 "How §4 is run"). It passed for 13dbe8f (locally 2026-10-17, the Preview check 2026-10-18; `readme/square-acceptance-2026-10-14.md`) (then §5 of the same runbook; S1–S4 are merged and live since 2026-10-13, #63). Deposit amounts read the policy from the `SiteSettings` row, never the day-cached `getSiteSettings()`. Money-safety rules (2026-10-13 review): outside a production build only SANDBOX credentials are usable (`usableSquareConfig`), so a preview or dev server can never move live money even if production vars leak into it; a refund claims SUBMITTING before Square is called and only a provable first send may end FAILED (a 4xx on a retry stays UNKNOWN for staff); Square's refund payload is payment + amount + key only (no free text), so a retry is byte-identical; a deliberate staff keep sets the attempt to KEPT (reconciliation never refunds it); declined cards are limited to 3 per account and 5 per IP a day (`createFailureLimiter`, never fails open). Review 2 (same day): only Square's HTTP 400/402 is a card decline — 401/403/404 and any other 4xx are the website's own Square setup (`FAILED` + `PAYMENT_SETUP_REFUSED`, customer told `PAYMENT_UNAVAILABLE`, no decline budget used, logged once per HTTP status, raised as a configuration problem); a deposit taken for a request nobody confirmed is lapsed and refunded only by the DAILY housekeeping run, 12 hours after its appointment ended (`TAKEN_DEPOSIT_LAPSE_GRACE_MS`; staff mark it completed to keep it, or decline it); `lastError` sentences that code reads back (Prisma `where`, `===`) are state keys pinned in `operations-messages.test.ts` — never reword one in place, add a key and a migration.
- **Square webhook and reconciliation (S4) — no polling cron.** `POST /api/webhooks/square` (`services/square-webhook-events.ts`) answers 404 while `usableSquareConfig()` is null and 413/401 (body over 64 KB, signature not matching the configured key and the CONFIGURED notification URL — never the Host header) before any DB access; event types it does not act on, other locations (also an event the schema cannot read that names one) and payments without a deposit reference (in-salon card-reader sales — Square notifies every payment on the account) are acknowledged before the database is opened (it is a public endpoint something external calls — see `neon-budget.md`); a refund (no reference to drop it by) whose payment is none of the site's deposits is looked up once and settled at once (`NOT_OURS`: never listed, emailed or re-read). Each `event_id` is stored once in `SquareWebhookEvent` (a repeat is a no-op); notices only move PAYMENT rows forward — Square's final COMPLETED/CANCELED/FAILED, never an older APPROVED — and never change a booking; a fresh CAPTURING claim is its approval's. When a notice says Square holds money no booking wants (an authorization that landed after the site gave up, a hold whose release failed) or took money the site believed held or released, the event stays open and the route reads Square afresh in `after()` and acts on THAT (`reconcileSquareEvent`). Reconciliation (`services/payment-reconciliation.ts`) rides the existing daily housekeeping run and Admin → Schedule → "Re-check payment" (`actions/admin-payments.ts`, admin-only, audited `PAYMENT.RECHECKED`): settles unanswered captures with S3's `settle`, releases AUTHORIZED holds whose booking is missing or not PENDING, confirms once with Square each hold S3 recorded EXPIRED by its date alone, cancels UNKNOWN authorizations by key every day for 7 days (cancel-by-key answers `{}` even when nothing has landed yet) then settles them VOIDED, resubmits REQUESTED/UNKNOWN refunds with the row's own key (each try dated on the row, so the batch — least recently tried first — rotates; 7 days after the refund was requested one that was sent becomes `UNRESOLVED`: counted, never resent, listed for staff) and follows PENDING ones, records a hold Square shows taken on a still-PENDING request as CAPTURED + `PAYMENT_CAPTURED_NOT_CONFIRMED` (a decline then refunds it at once; confirming still works), and refunds in full (`LATE_CAPTURE`) a deposit Square took after its booking closed or was never made. Every gateway comes from the guarded path (`depositGatewayFor` / `usableSquareConfig`; `createSquareGateway` has no default config) and only for the deposit's own Square environment and location. What still needs a person — Square refusing deposits because of the website's own setup (401/403/404), unanswered deposits, money taken on an unconfirmed request or on a cancelled booking with no refund or keep recorded, unreleased holds, failed, unanswered or `UNRESOLVED` refunds, late captures, unmatched notifications — is `services/payment-attention.ts`: the daily "needs attention" email (`PAYMENTS_NEED_ATTENTION`) and Admin → Operations → "Payments needing attention". Staff close a refund they settled themselves (Square Dashboard or cash) with the booking dialog's "Mark refund as settled outside the website" (`markRefundSettledOutside`, admin-only, audited `PAYMENT.REFUND_SETTLED_OUTSIDE`: REQUESTED / UNKNOWN / UNRESOLVED / stale SUBMITTING → `SETTLED_EXTERNALLY`, counted, never sent again). Dev, unit tests and CI integration scripts are not locked; a local `pnpm build && pnpm start` rehearsal is (without production Square credentials). **Runbook** (what the site does at each step, env vars, sandbox setup on Preview, acceptance tests, production go-live, staff operations, preview-database migration): `docs/square-payments-setup.md`. The customer-facing rules live on `/booking-terms` (`legal.bookingTerms`, its notice and patch-test periods read from code constants) and in the privacy notice — keep both true when the payment rules change.
- **24-hour cancellation/reschedule policy** — enforced server-side in booking actions; a reschedule request's new time must also be ≥ 24 h away.
- **48-hour deposit rule (owner decision 2026-10-18).** A customer cancelling a CONFIRMED booking `DEPOSIT_REFUND_NOTICE_HOURS` (48) or more before its start (exactly 48 h counts, `isDepositRefundableOnCancel`) gets the deposit refunded in full (`CUSTOMER_CANCELLED`); less than that — online until 24 h before, by phone after — it is kept. `cancelAppointment` decides inside its Serializable transaction from the booking's start and the time now, and keeps it through the staff-keep outcome (`planDepositForClosing` with `refund: false` → attempt `KEPT`, no refund row, reconciliation never refunds it; the CANCELLATION email says kept). My Bookings (`AppointmentCard`) says before the customer confirms whether the deposit is refunded or kept and passes `{ depositKept }`; a cancellation that would keep a deposit without that is refused (`DEPOSIT_NOW_KEPT`) and changes nothing (the 48-hour mark passed while the dialog was open), and the card then shows the kept wording. PENDING requests are unchanged (withdrawing releases the hold; money taken on a request is refunded). Staff cancelling keep choosing (refund ticked by default — the salon's own cancellations are refunded; untick for a customer who phones inside 48 h). The booking page's deposit notice (with a 48-hour warning beside the 24-hour one), `/booking-terms`, the confirmation and cancellation emails and the admin dialog's help read the constant; the late-arrival auto-cancel (KEPT as a no-show) is unchanged. **A reschedule asked for inside 48 hours keeps the lock (option A, owner 2026-10-18):** when staff approve a customer request made less than 48 hours before the booking's then start (`rescheduleRequestedAt` vs the old start), `decideRescheduleRequest` sets `Appointment.depositLockedAt` (never cleared), and `isDepositRefundableOnCancel(start, now, depositLockedAt)` answers kept whatever the new time — so "move, then cancel" cannot turn a kept deposit into a refund. The reschedule dialog warns before sending, My Bookings and the admin cancel dialog say so, and the RESCHEDULE/CANCELLATION emails carry `depositLocked`. Staff moves are not locked (staff choose in the cancel dialog).
- **Customer reschedules are staff-approved requests** (`requestReschedule` → `decideRescheduleRequest`); the booking stays CONFIRMED at its original time until approval, which refreshes the stylist's Fresha feeds and re-checks the slot in a Serializable transaction. Unanswered requests lapse 24 h before the requested time (notifications cron).
- **Night behaviour (owner decision 2026-11-08): only the inbound sync stops.**
  - The Fresha/Treatwell import runs in staff hours only (`isScheduledCalendarSyncOpen`). A feed's age is measured from the moment it last had the chance to run (`calendarFreshnessReference`): now during the day, the pause time after closing, and last evening's pause in the first 90 minutes of the morning. A feed already stale when the import paused, or one that has never succeeded, still closes booking at night.
  - Customers can request a booking at night. The website cannot see what a marketplace sold overnight; that is safe because a request holds nothing firm until staff confirm it.
  - Staff confirm by hand at any hour. `updateAppointmentStatus`, `approveWithDeposit` and `decideRescheduleRequest` never call `checkCalendarBookingReadiness`. They run `refreshCalendarFeedsBeforeApproval` for that stylist only, best-effort and outside the transaction, then the slot check inside it. A feed that cannot be read never stops a confirmation.
  - Outbound has no hours: every confirmed change drops the busy feed's cache and schedules the Google push (`invalidateStylistIcalFeed`).
- **When booking closes itself** (`services/booking-closed-alert.ts`, from the calendar-sync cron): `bookingEnabled` on but the calendar check or the Operations report failing sends the salon one email a London day (`booking-closed/<day>`), recorded in the `booking-closed-alert` job row. A failed diagnostics run closes booking until one passes; `runOperationsDiagnosticsAction` says so when booking is on.
- **A reminder waits `REMINDER_MIN_HOURS_AFTER_CONFIRMATION` (12) after the confirmation** (`isReminderDueAfterConfirmation`, enqueue only), or a booking confirmed 24–36 hours ahead is reminded within half an hour of its confirmation email.
- **Consultation credit** (`services/consultation-credit.ts`, spec `2026-10-16-consultation-credit-pricing-ux-design.md` §2): a paid consultation or patch test (COMPLETED, or CONFIRMED and started and not late-cancelled) is taken off a consultation-required treatment starting within `CONSULTATION_CREDIT_MONTHS` (6, salon-local calendar months), **used once**: a live booking holding it uses it up, and a cancelled treatment frees it. **Staff apply it, in Admin only** (online customers cannot book consultation-required services): the booking dialog previews it (`actions/admin-consultation-credit.ts`) and `createAppointmentByAdmin` / `editAppointmentByAdmin` — and a late-cancellation restore — **look it up again inside the booking's Serializable transaction**, never trusting an amount from the browser. Capped at the price less any captured deposit; recorded beside the price (`consultationCreditFromId`, `consultationCreditPence`) — `priceAtBooking` / `quoteJson` never change. Shown as "Consultation credit −£X" plus what is left to pay on the confirmation and reminder emails, My Bookings and the admin board (not on a cancelled booking). Treatments booked through Fresha or by phone outside Admin are not tracked: staff deduct the fee at the till (`LAUNCH.md` §4).
- **Price after consultation:** `effectivePriceNature(service)` (`services/pricing/policy.ts`) makes a consultation-required service's price `SUBJECT_TO_CONSULTATION` whatever its row stores — a code rule, not per-service data. It is applied to the public catalogue (`public-catalog.ts`: "From £X — final price confirmed at your consultation", JSON-LD `minPrice`) and to every recorded quote (`buildQuote`), so confirmations, reminders and My Bookings never state a fixed amount left to pay for such a booking.
- **NHS/student prices and offer terms:** an NHS-priced option (`requiresEligibilityProof`, `services/pricing/eligibility.ts`) carries the `pricing.eligibilityProof` notice (bring an NHS staff ID or student card, else the standard price applies) in the booking wizard, the request, confirmation and reminder emails and My Bookings. The five offer and discount-code terms (`legal.bookingTerms.offers`, rendered by `components/legal/OfferTerms.tsx`) appear on `/booking-terms` and `/offers`. Discount codes stay paused (`DISCOUNTS_PAUSED` in `services/pricing/policy.ts`, a constant); before unpausing, those terms must be enforced in code, not only stated.
- **Who customers see, who takes walk-ins** (owner, 2026-10-17). Two switches per stylist, in the Admin → Stylists list (one click, `setStylistSwitch`) and on the Edit page:
  - **Show on website** (`Stylist.showOnWebsite`; a stylist made in Admin → Stylists starts hidden, and hidden → shown is refused without a full valid week, `HOURS_NEEDED`, because one visible stylist without hours closes booking for everyone, review 2026-11-08). Off: left out of every public stylist query (`stylists/slug.ts`, sitemap), the `/book` list, "Anyone" (`getAvailableSlotsUnion`, `getBookingDays(ANY)`, `eligibleStylistIds`) and the online-booking coverage gate (`getCalendarSyncCoverage`, so a new starter with no rota or Fresha feed never closes booking), and `createBooking` / `createBookingForFirstAvailable` / `precheckBookingRequest` refuse them (`assertShownOnWebsite`, `STYLIST_UNAVAILABLE`). Their times still read by name (a customer rescheduling an existing booking uses the same lookups), and they stay in Admin, the Google diary, staff bookings and their Fresha feed. Admin lists come from `getStylistsForAdmin` / `getStylistById`, never the public helpers.
  - **Takes walk-ins** (`Stylist.takesWalkIns`): the chair rule (`architecture.md` → Calendars → Diary mirror).
  - **Admin → Employees → "Also add as stylist"** (new employee, or one never linked): `services/stylist-from-employee.ts` makes the linked stylist in the employee's transaction: the employee's name, the job title as the role in both languages (published and marked reviewed), **hidden from the website**, takes walk-ins on, a free slug (`mei`, `mei-2`…). Picking an existing stylist as well is refused (`STYLIST_BOTH`).
- **Admin calendar drags and resizes ask first** (`components/admin/MoveConfirmDialog.tsx`): nothing is saved until staff press Move; focus starts on Cancel, and clicks in the first 350 ms are ignored (iPad ghost taps).

## Booking and operations rules (2026-10-13 review — keep them)

- **Online requests need `MIN_BOOKING_NOTICE_MINUTES` (120) notice** (`lib/booking-constants.ts`); staff-entered bookings are exempt. A repeat submission (same customer, service and start — with the same stylist when one is named, any stylist for "Anyone") returns the existing request instead of booking twice, and the wizard says it was already requested; the same time with a different named stylist is a deliberate second booking. When a deposit is due the same rule (`findExistingRequest`, sharing `repeatRequestWhere` with `findRepeatRequest`) is checked before the card is touched, so a repeat never authorizes a card; keep the two lookups on one rule.
- **Unanswered requests lapse once their appointment has ended** (start + `durationAtBooking ?? service.duration`, `hasAppointmentEnded`; `services/pending-request-lapse.ts`, run by the notifications cron and by housekeeping) — never at the start: a staff pencil-in is PENDING too, its customer may be in the chair, and a cancelled booking leaves the busy feed at once. Staff cannot confirm a request that has started, but can mark it completed or decline it; a decline after the start sends the `REQUEST_LAPSED` email under the lapse step's own rule (`services/request-lapse-notice.ts`: only for an online request — known by its version-0 salon alert since `REQUEST_RECEIVED` was retired — never a staff pencil-in); a decline before the start sends the `CANCELLATION` email (`wasConfirmed: false`) as always. Cron code invalidates the busy feed with `invalidateStylistIcalFeedFromCron()` — `updateTag` only works in Server Actions.
- **"Mark completed" only once an appointment has started** (a confirmed booking, or a started request whose customer came in). The outbound busy feed exports every non-cancelled booking until it ends, completed ones included, so Fresha cannot resell a chair that is still in use.
- **Late arrivals** (`services/late-arrival-cancel.ts`, rules in `lib/late-arrival.ts`, constants in `lib/booking-constants.ts`, spec `2026-10-16-late-arrival-auto-cancel-design.md`): switched on in Admin → Settings (`SiteSettings.lateAutoCancelSince`, off by default; read from the live row, never the cached settings). The calendar-sync cron (no new cron; it needs `CALENDAR_SYNC_ENABLED=true` and runs in staff hours) then cancels, at its first tick 15 minutes or more after the start, a CONFIRMED booking not marked Arrived, only if it was both created and starts after the switch-on, started within the last 120 minutes and has no open customer reschedule request. The deposit is kept (KEPT, as a no-show) and `LATE_CANCELLED` is emailed 30 minutes later. Staff tap Arrived (arrivals panel `components/admin/LateArrivalPanel.tsx` / booking dialog; `markArrived` in `actions/admin-arrivals.ts`) or move the booking when a customer phones ahead; Mark completed and staff bookings starting within 15 minutes of entry count as arrived. A move outside the arrival window clears the arrival, unless the customer is already there and it stays the same day. Restore within 24 h (`restoreLateCancellation`, audited `APPOINTMENT.LATE_CANCEL_RESTORED`: KEPT → CAPTURED, drops the unsent email, re-checks any consultation credit). The privacy notice describes it as the one automated decision.
- **Calendar files** (`lib/calendar-links.ts`) — the customer's side, Google Calendar option A: links and files only, no Google API (the salon calendar's two-way sync, in `architecture.md` → Calendars, is separate):
  - Confirmed bookings carry an "Add to Google Calendar" link and an RFC 5545 `.ics` on the confirmation, reschedule and reminder emails and on My appointments.
  - The emailed file has an ORGANIZER and a matching `method` on its MIME type.
  - A cancellation sends `METHOD:CANCEL` only when the booking had been confirmed (`wasConfirmed`); a request that was never confirmed gets no calendar file.
- **Email verification is GET → confirm page → POST.** Never verify (or consume anything) on a GET: mail scanners open every link. Every public form that sends email (registration, verification resend, password reset, marketing unsubscribe) shares a 20-per-IP daily cap and a 40-a-day site-wide cap (`emailSendDailyLimiter`, so public forms can never spend Resend Free's 100 a day and starve booking mail).
- **Customer erasure goes through Admin → Users** (`actions/admin-erasure.ts`, `docs/data-erasure.md`): anonymise, never delete a customer row (it cascades the booking history). The privacy notice (`messages/*/legal.ts`) states retention periods — keep it true when retention code changes.
- **Every fixed `lastError` sentence a job writes is catalogued** in `services/operations-messages.ts` (a test enforces it) so Admin → Operations can translate it.
- **No `images.remotePatterns`.** Remote images render as plain `<img>`; a remote pattern lets anyone run billed optimisations on that host.
- **The monochrome brand is enforced by `src/app/brand-monochrome.test.ts`.**
- **Deploys are serialised** (`deploy.yml` concurrency: runs on main queue and are never cancelled mid-flight; a queued run is superseded by a newer one, so the newest commit deploys last; the Vercel CLI is pinned — bump it on purpose). With the `NEON_API_KEY` secret and `NEON_PROJECT_ID` variable set, each production deploy first takes a compute-less Neon branch (`predeploy-*`, newest three kept).
- **A skip-CI marker in main's head commit message deploys nothing.** GitHub runs no workflow for a push whose head commit message contains `[skip ci]`, `[ci skip]`, `[no ci]`, `[skip actions]` or `[actions skip]` — even quoted inside an explanation — and a squash merge copies every commit message of the PR into one body. On 2026-10-13 #62's squash body quoted the marker, so its push ran no CI and no deploy, and production silently stayed on the old code until the next push. In commit messages write "skip-ci marker", never the bracketed form; before merging, check the squash body (or pass `gh pr merge --squash --body …`); after merging, confirm a `push` run for the new main SHA appears in Actions.
