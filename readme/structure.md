# Project Structure

## Overview
This document tracks the architectural structure of the Harbour Hair Salon project.

## Directories
- `app/`: Next.js App Router routes and pages.
- `components/`: Reusable UI components.
- `lib/`: Shared utilities and Prisma client.
- `services/`: Business logic and service layer.
- `types/`: Shared TypeScript definitions.
- `prisma/`: Database schema and migrations.
- `readme/`: Project documentation.

## Key Components

### Try-Color (Virtual Hair Color Try-On)
- `src/app/[locale]/try-color/page.tsx` — Server page with metadata
- `src/app/[locale]/try-color/TryColorClient.tsx` — Main client orchestrator. Modes: `upload` (photo) and `video`; live camera is retained but disabled behind `ENABLE_LIVE_CAMERA = false`. Memoizes the shared `HairConsultation` recolor request, paints photos after canvas mount, clears stale media analysis and receives photo/video result context.
- `src/components/try-color/CameraView.tsx` — Camera feed (currently flag-disabled, code retained)
- `src/components/try-color/VideoTryOn.tsx` — Video-clip try-on: uploads a short clip, extracts/segments frames (`segmentStill`), recolors source copies, reports current-frame analysis via `onContextChange`, and plays with scrub + download-still. Replacement/unmount invalidates pending extraction. Guardrails: `VIDEO_MAX_SECONDS`, `VIDEO_MAX_DIM`, `VIDEO_TARGET_FPS`, `VIDEO_MAX_FRAMES`, `VIDEO_MAX_FILE_BYTES`, plus a slow-device fallback.
- `src/components/try-color/PreviewCanvas.tsx` — Photo preview/download surface; contains the full image without cropping hair.
- `src/components/try-color/segmentation.worker.ts` — Worker: MediaPipe segmentation (used by the flag-disabled live path)
- `src/components/try-color/HairSegmentation.ts` — Singleton ImageSegmenter + `segmentStill()` for photos and video frames
- `src/components/try-color/colorMath.ts` — `analyzeHair` samples hair interiors with trimmed statistics, exposure/support checks, D65 Lab and approximate photographic zones. `resolveRecolorContext` models deposit/permanent/prelighten scenarios with history restrictions and translated notice codes; `applyRecolorToImageDataWithAlpha` preserves source texture and exact zero-strength identity. These are uncalibrated visual heuristics, not salon outcome guarantees.
- `src/components/try-color/constants.ts` — `HairConsultation`, `RecolorRequest`, quality/notice types and illustrative shade provenance. Generic preview levels stay separate from manufacturer scales; presets/custom colours share an sRGB derivation with continuous rendering luminance. MediaPipe/video constants remain here.
- `src/components/try-color/ColorPalette.tsx` — Shade selection, visual strength, service/history/white-hair/base controls, quality/range/zone summaries and bilingual capture guidance.
- `src/components/try-color/tressCalibration.ts` — Validated offline real-tress measurement schema and `deltaE2000` for like-for-like colour differences. `scripts/validate-hair-calibration.ts` checks a supplied JSON dataset without publishing it; `readme/try-color-calibration.md` documents source research, collection and independent validation. No measured manufacturer records are bundled.
- `src/components/try-color/UploadDropzone.tsx` — Photo validation/decoding; replacement or unmount cancels pending callbacks and releases object URLs.
- `next.config.ts` / `src/app/lib/try-color-media.test.ts` — Shared CSP permits same-origin and local `blob:` media so video works after direct or soft navigation.
- `src/components/try-color/ResultActions.tsx` — Download button

### Colour Booking Gate (Consultation & Patch Test)
Colour services (`Service.requiresPatchTest`) require a COMPLETED Consultation & Patch Test (`Service.isPatchTest`) appointment ≥48h before and within 6 months of the colour date.
- `src/app/services/patch-test-eligibility.ts` — Pure logic: `evaluatePatchTestEligibility(tests, colourDate)` → `{ ok, testDate, reason }`; constants `PATCH_TEST_MIN_LEAD_HOURS` (48), `PATCH_TEST_VALIDITY_DAYS` (183). Unit-tested in `patch-test-eligibility.test.ts`.
- `src/app/services/booking-service.ts` — `getValidPatchTest(userId, colourDate, db?)` queries the user's patch-test appointments and delegates to the pure function; a caller inside a transaction passes its `tx` (reschedule approval).
- `src/app/actions/booking.ts` — `submitBooking` and `requestReschedule` / `withdrawRescheduleRequest` enforce the gate server-side; `checkColourEligibility(serviceId, dateIso)` powers the wizard UX. `requestReschedule` answers a request for the booking's current (or already-requested) instant as a no-op success (no version bump, no email), and caps real requests with `rescheduleLimiter` (5/h per customer) and `appointmentRescheduleLimiter` (3/24h per appointment) → `TOO_MANY_RESCHEDULES`.
- `src/components/booking/BookingWizard.tsx` — Shows a blocking gate panel + "book Consultation & Patch Test first" CTA at the CONFIRM step; disables submit when ineligible.
- `src/app/actions/admin.ts` — `updateAppointmentStatus(appointmentId, status)` (admin-only) marks appointments COMPLETED — the signal that unlocks colour booking. COMPLETED only once the visit has started (`COMPLETE_BEFORE_START`; a started PENDING request may be completed too), CONFIRMED only before a request's time (`REQUEST_EXPIRED`); a staff cancellation of a booking that has already started sends no cancellation email — except that declining a started PENDING request sends `REQUEST_LAPSED` under the lapse step's rule (`request-lapse-notice.ts`). A cancellation records `wasConfirmed` for its calendar file.
- `src/components/admin/ScheduleCalendar.tsx` — "Mark completed" control (`canMarkCompleted`) on CONFIRMED and PENDING appointments that have started, behind a confirm prompt.
- `src/app/lib/appointment-timing.ts` — `hasAppointmentStarted(date, now)` (pure, client-safe): the one "has this visit begun?" rule shared by the board, the status action and the request lapse; `hasAppointmentEnded(date, minutes, now)`: start + duration has come (the busy feed's own `end <= now` boundary) — the request lapse waits for it.
- `src/components/admin/AppointmentDialog.tsx` — create/edit bookings; an explicit, confirmed "Cancel booking" action releases pending/confirmed bookings through the existing authenticated status action, audit trail, notification outbox and feed invalidation.
- `src/components/admin/ServiceForm.tsx` + `src/app/actions/admin-services.ts` — manage `requiresPatchTest`/`isPatchTest` per service.

### Customer Reschedule Requests
A customer's move of a CONFIRMED booking is a request; the original time stays booked until staff decide.
- `src/app/lib/reschedule-request.ts` — `RESCHEDULE_REQUEST_LEAD_HOURS` (24), `isRescheduleRequestExpired`, `isRescheduleRequestMoot` (requested time < 24 h away **or** the original time has passed), `rescheduleRequestView` (pure, client-safe).
- `src/app/actions/booking.ts` — `requestReschedule(appointmentId, dateStr, time)`, `withdrawRescheduleRequest(appointmentId)`; `cancelAppointment` clears an open request.
- `src/app/actions/admin.ts` — `decideRescheduleRequest(appointmentId, 'APPROVE' | 'DECLINE', requestedAt)`; approval first runs `refreshCalendarFeedsBeforeApproval(stylistId)` (that stylist's feeds older than `APPROVAL_REFRESH_MINUTES` = 5, then every stylist's feeds older than `CALENDAR_POLL_MINUTES` = 30 or failing), exactly as new-booking approval does.
- `src/app/services/reschedule-request-lapse.ts` — `lapseExpiredRescheduleRequests(now)`, run by the notifications cron; also clears requests on bookings whose original time has passed (audited, no email).
- Emails: `RESCHEDULE_REQUEST_RECEIVED`, `SALON_RESCHEDULE_ALERT`, `RESCHEDULE_DECLINED`, `RESCHEDULE_LAPSED` (keyed by the request's `requestedAt`).

### Booking-request lapse
A booking request (PENDING) left unanswered lapses once its appointment has ended (owner policy, 2026-10-13); from its start it can no longer be confirmed.
- `src/app/services/pending-request-lapse.ts` — `lapseStartedPendingRequests(now)`: per started PENDING row whose appointment has ENDED (`hasAppointmentEnded` on `durationAtBooking ?? service.duration`, re-checked in the row's transaction; a request still under way is skipped, not failed — staff can mark it completed meanwhile, the board offers that on started requests), a conditional write to CANCELLED (version bump, Treatwell sync like a staff cancellation), audit `APPOINTMENT.LAPSED`, and a `REQUEST_LAPSED` email only when the customer had a `REQUEST_RECEIVED` (a staff pencil-in is closed silently) and only within `REQUEST_LAPSE_NOTICE_HOURS` (72) of the requested time — enforced again at dispatch, so a backlog or mail held while sending was off is never sent late; drops the busy feed with `invalidateStylistIcalFeedFromCron` (`stylist-ical-cache.ts`, `revalidateTag(..., { expire: 0 })` — `updateTag` throws in Route Handlers). Run by the notifications cron and by `/api/cron/housekeeping` (so it also happens while sending is off).
- `src/app/services/request-lapse-notice.ts` — `isRequestLapseNoticeDue(tx, request, now)`: the one rule for the `REQUEST_LAPSED` email (an online request — its version-0 salon alert exists, `onlineRequestAlertKey(id)`, or an old `REQUEST_RECEIVED` row from before 2026-10-18; never a staff pencil-in — AND `isRequestLapseNoticeTimely`), shared by the lapse step and by staff declining a PENDING request once its time has come (`updateAppointmentStatus`, which the lapse step then skips); `readSalonPhoneForLapseNotice(db)` — best-effort salon phone for that email's callout.
- `src/app/services/admin-calendar-data.ts` — the "awaiting confirmation" queue and count list only requests whose time is still ahead; the calendar views still show the rest.

### Late arrivals (Admin → Schedule, Admin → Settings) — spec `docs/superpowers/specs/2026-10-16-late-arrival-auto-cancel-design.md`
A CONFIRMED booking nobody marks Arrived within 15 minutes of its start is cancelled by the calendar-sync cron. Ships OFF (`SiteSettings.lateAutoCancelSince = null`); the Admin → Settings switch stamps the instant it was turned on, and only bookings made and starting after it, with no reschedule request open, are ever touched.
- `src/app/lib/late-arrival.ts` — pure, client-safe timing rules: `lateCancelDueAt`, `isArrivalWindowOpen` (an hour before the start until the later of its end and 120 minutes), `lateCancelWindow`, `lateCancelReaches` (will the rule ever reach this booking: on, CONFIRMED, not arrived, no reschedule request open, made and starting after the switch-on — the cron and the panel share it), `isLateCancelCandidate`, `isLateCancelRestorable` (24 h). Constants in `booking-constants.ts` (`LATE_ARRIVAL_CANCEL_MINUTES`, `LATE_ARRIVAL_LOOKBACK_MINUTES`, `LATE_CANCEL_EMAIL_DELAY_MINUTES`, `LATE_CANCEL_RESTORE_HOURS`, `ARRIVAL_EARLY_MINUTES`). Unit-tested in `late-arrival.test.ts`.
- `src/app/services/late-arrival-cancel.ts` — `cancelLateArrivals(now, { limit })`: reads the live settings row (never the day cache) before anything else, then per candidate a Serializable transaction that re-reads the switch and the booking and closes it behind a conditional write (`status`, `arrivedAt`, `rescheduleRequestedAt`, `date`), so a staff "Arrived" (or a customer's reschedule request) always wins. Sets `lateCancelledAt`, bumps `notificationVersion`, Treatwell sync like a staff cancellation, plans the deposit closing with `refund: false` (a taken deposit becomes `KEPT`, no Square call; a capture in flight skips the booking to the next run), queues `LATE_CANCELLED` with `notBefore` now + 30 minutes, audits `APPOINTMENT.LATE_AUTO_CANCELLED`, then drops the busy feed (`invalidateStylistIcalFeedFromCron`). Called by `/api/cron/calendar-sync` after its `CALENDAR_SYNC_ENABLED` and staff-hours gates (job row `late-arrival-cancel`, failures as `LATE_ARRIVAL_FAILED`). Unit-tested in `late-arrival-cancel.test.ts`; the real-PostgreSQL race and restore are in `scripts/verify-booking-lifecycle.ts`.
- `src/app/actions/admin-arrivals.ts` — `markArrived(appointmentId, arrived)` (admin-only, CONFIRMED only — a booking the rule cancelled answers `LATE_CANCELLED_USE_RESTORE` — inside the arrival window, conditional write; audit `APPOINTMENT.ARRIVED` / `ARRIVAL_CLEARED`) and `restoreLateCancellation(appointmentId, { force })` (within 24 h; booking CONFIRMED + arrived and deposit KEPT → CAPTURED in one transaction, clashes reported unless forced, bumps the version so an unsent `LATE_CANCELLED` is dropped; audit `APPOINTMENT.LATE_CANCEL_RESTORED`). Marking completed and staff walk-ins (a start within the next 15 minutes) also set `arrivedAt` (`admin.ts`, `admin-schedule.ts`); a staff move to a start outside the arrival window clears it. `reschedule-request-lapse.ts` keeps a request whose original start has come until the 120-minute lookback has passed.
- `src/app/services/late-arrival-board.ts` — `getLateArrivalBoard(now)`: the rows for Admin → Schedule's panel (due or soon-due bookings, and recent late cancellations with whether their email was sent). `src/components/admin/LateArrivalPanel.tsx` renders it with the Arrived and Restore buttons; `AppointmentDialog.tsx` and the schedule grids carry the same toggle and an "arrived" mark.
- Email: `LATE_CANCELLED` (`notification-outbox-service.ts` current-check: still CANCELLED with `lateCancelledAt` set, and not more than a day after the start). Wording in `messages/{en,zh}/emails.ts`; the customer-facing rule is on `/booking-terms` and My appointments.

### Consultation credit, price after consultation, move confirmation, eligibility notices — spec `docs/superpowers/specs/2026-10-16-consultation-credit-pricing-ux-design.md`
A paid consultation's fee comes off the consultation-required treatment it was for (once, within 6 months); consultation-required prices read "From £X — final price confirmed at your consultation"; dragging a booking asks first; NHS/student prices ask for proof.
- `src/app/services/consultation-credit.ts` — `pickConsultationCredit(rows, { at, now, excludeAppointmentId, preferAppointmentId })` (pure: a consultation or patch test of this customer's, COMPLETED or CONFIRMED-and-started and not late-cancelled, priced > £0, within `CONSULTATION_CREDIT_MONTHS` salon-local calendar months — `consultationCreditWindowStart` — and not held by another live booking; the most recent wins, unless the booking's own recorded one still qualifies); `findConsultationCredit(db, …)` (the query feeding it); `creditFor(credit, pricePence, capturedDepositPence)` (capped at the price less a taken deposit, never below 0); `findApplicableConsultationCredit(db, …)` (null when nothing would be deducted, so a consultation is never used up for £0) and `capturedDepositPence(attempt)`. Unit-tested in `consultation-credit.test.ts`.
- `src/app/actions/admin-consultation-credit.ts` — `previewConsultationCredit({ customerId | email | appointmentId, serviceId, dateStr, time })`: admin-only, read-only answer for the booking dialog (the edited booking's recorded price and taken deposit, else the listed price). Saving never trusts it: `createAppointmentByAdmin` / `editAppointmentByAdmin` (`admin-schedule.ts`, `applyConsultationCredit`) look the credit up again inside their Serializable transaction and write `Appointment.consultationCreditFromId` / `consultationCreditPence`; `restoreLateCancellation` (`admin-arrivals.ts`) re-checks a recorded one (kept / reassigned / cleared, audited). `priceAtBooking` / `quoteJson` never change. Tests: `admin-consultation-credit.test.ts`, `admin-arrivals.test.ts`.
- `src/components/admin/ConsultationCreditOption.tsx` — `useConsultationCreditPreview(lookup)` (debounced; an answer only for the question it answered) and the dialog's "Consultation credit available — deduct from this booking" box (ticked by default for a new booking; an edit starts as the booking stands). `AppointmentDialog.tsx` sends the box only when it was shown, and Save waits while the credit is being checked.
- Showing it: `email-content.ts` (credit row, what is left to pay on the confirmation and reminder, the consultation's own "credited within 6 months" footnote; snapshot fields `consultationCreditPence`, `isConsultation` in `notification-outbox-service.ts`), `AppointmentCard.tsx` (My Bookings), `ScheduleCalendar.tsx` (day list). A CANCELLED booking shows none.
- `src/app/services/pricing/policy.ts` — `effectivePriceNature(service)`: a consultation-required service's price is `SUBJECT_TO_CONSULTATION` whatever its row stores. Used by `public-catalog.ts` and by `buildQuote` (`quote.ts`), so recorded quotes carry the caveat too. `PriceParts.tsx`: `useFormatServicePrice` ("From £X"), `ConsultationCreditNote` (the promise under a price); `json-ld.ts`: `minPrice` for such services.
- `src/app/services/consultation-routing.ts` — `consultationFeeByServiceId(services)`: each consultation-required service's consultation price (pence), from the wizard's own routing; the services pages pass it to `ConsultationCreditNote`.
- `src/components/admin/MoveConfirmDialog.tsx` — "Move this booking?" after a drop or resize in `ScheduleDayGrid` / `ScheduleWeekGrid` (only what changed: time, stylist, length); focus on Cancel, Esc cancels, clicks in the first 350 ms are ignored (iPad ghost tap), nothing is sent before Move. A cancelled pointer snaps back without asking. Tests: `ScheduleMoveConfirm.test.ts`.
- `src/app/services/pricing/eligibility.ts` — `requiresEligibilityProof(service)`: an NHS-type price ("NHS", "Student & NHS") needs proof at the appointment; the notice shows on the services pages, the wizard's option chooser and confirm step, the request/confirmation/reminder emails and My Bookings.
- `src/components/legal/OfferTerms.tsx` — `OFFER_TERM_KEYS` + `OfferTerms`: the offer, discount-code and NHS/student terms (`legal.bookingTerms.offers`) on `/booking-terms` and `/offers`. `DISCOUNTS_PAUSED` (policy.ts) lists what must be built before codes return.
- `prisma/{dev,prod,vercel}/migrations/20261016140000_consultation_credit/migration.sql` — the self-relation and its index (SQL Server: NO ACTION).

### Opening Hours (Admin → Opening Hours)
The hours the booking engine sells from. Before this, `Availability` was written only by `prisma/seed.ts` — production had no way to change it.
- `src/app/services/opening-hours.ts` — pure, dependency-free: `validateWeek(days)` (structure, time format, close-after-open, normalises closed days), `countSlots(start, end, duration)` and `DAY_NAMES`. Unit-tested in `opening-hours.test.ts`; `countSlots` is pinned against the booking engine's own `buildSlotsForWindow` so the two cannot drift.
- `src/app/actions/admin-availability.ts` — `updateStylistAvailability` replaces one stylist's whole week in a `$transaction` of upserts. Admin-gated and validated before any write (locked by `opening-hours-schema.test.ts`). A failed write answers in the form (`SAVE_FAILED`, edits kept) instead of throwing to the error boundary.
- `src/app/[locale]/admin/opening-hours/page.tsx` — pads stylists with fewer than seven rows to a full week; explicit `select` so the secret `treatwellIcalUrl`/`icalToken` never reach the client.
- `src/components/admin/OpeningHoursForm.tsx` — stylist tabs, per-day open/closed + time inputs, live slot-count preview, copy-hours-to-all-open-days.

### Marketplace channels
Public booking buttons come from the URLs in Admin → Site Settings. Calendar readiness is configured separately per stylist/provider in Admin → Integrations.
- `src/app/services/marketplace-channels.ts` — pure `activeMarketplaces(settings)` → `{name, url}[]` for any non-empty `freshaUrl` / `treatwellUrl` / `booksyUrl`. Unit-tested.
- `/book` renders one CTA per configured public marketplace while booking is closed. Clearing a public URL removes its button; it does not change a calendar connection's `receivesBookings` flag or remove readiness requirements.
- `evaluateSyncCoverage` checks Fresha and Treatwell ICS connections for every stylist/provider marked `receivesBookings`: valid weekly hours, a successful inbound attempt within 90 minutes with no latest error, and confirmed subscription to the matching website Busy feed. ICS polling reduces conflicts but cannot guarantee an atomic cross-platform reservation.
- `booking-maintenance.ts` deliberately contains **no** marketplace name or URL; `booking-maintenance-copy.test.ts` locks that, because the old hardcoded `TREATWELL_BOOKING_URL` fallback made the Treatwell button impossible to switch off from the admin panel.

### Customer data erasure (Admin → Users) — procedure in `docs/data-erasure.md`
- `src/app/actions/admin-erasure.ts` — `eraseCustomerData(userId, confirmation)`: admin-only; refuses ADMIN accounts, the acting admin, already-erased accounts and customers with upcoming PENDING/CONFIRMED bookings. One serializable transaction anonymises the User (row kept — deleting it cascades the appointment history), deletes OAuth links and reset links, clears appointment notes/language, stops and empties outbox copies, audits `USER.ERASED` (counts only); then best-effort removal from the Resend marketing audience.
- `src/app/lib/customer-erasure.ts` — `ERASED_CUSTOMER_NAME`, `erasedEmailFor` (`erased-<id>@erased.invalid`), `isErasedEmail`, `erasureConfirmationFor`/`erasureConfirmed` (their email, or `ERASE` for a phone booking). `lib/walk-in-customer.ts` `isPlaceholderEmail` also covers the erased domain, so nothing is ever queued for it.
- `src/components/admin/CustomerErasureSection.tsx` (server, `?erase=` search, ≥ 2 characters, ≤ 10 matches, names in any case) + `EraseCustomerButton.tsx` (typed-confirmation prompt).
- `review-service.ts` shows an erased customer's review under the anonymous label; `searchAdminCustomers` never offers an erased account, and `createAppointmentByAdmin` refuses one a still-open dialog picked (`CUSTOMER_GONE`).
- `src/app/actions/admin.ts` `createAdminUser` stores the email trimmed and lower-case (sign-in looks it up that way).

## Services
- `deposit-policy.ts` — pure GBP/pence deposit calculation from explicit server-owned policy and net price; no deposit terms are enabled automatically.
- `deposit-quote.ts` — `depositForQuote({ quoteAmountPence, settings, overridePence })` → `{ depositPence, remainderPence, policy }` (pure, via `calculateDepositPence`; an impossible policy throws); `readDepositSettings(db)` reads the policy from the `SiteSettings` row, never the cached `getSiteSettings()` (a never-saved row = off); `quoteDepositForNewBooking(db, serviceId)` = `quoteForNewBooking(…, 'CUSTOMER')` + policy + the service's `depositOverridePence`. See "Square deposits" below; unit-tested.
- `square-gateway.ts` — disabled-by-default, server-only Square REST adapter for authorization (optional `note`, ≤ 500 chars, no personal data), capture, cancellation, retrieval and refunds. `submitBooking` authorizes deposits through it (`payment-attempts.ts`, phase S2); approval captures, closings release or refund (`deposit-lifecycle.ts`, phase S3); reconciliation reads, releases and refunds (`payment-reconciliation.ts`, S4). `loadConfig` is required (S4): it must come from `usableSquareConfig()` / `depositGatewayFor`, never the raw `getSquareConfig()`. See `docs/square-payments-setup.md` and `pnpm test:square`.
- `booking-service.ts` — slot availability, booking creation, patch-test eligibility query
